用語解説 (非エンジニア向け)

以降の説明に出てくる技術用語を、家・お店に例えて先にまとめます。

用語 ひとことで言うと Light Survey での役割
Supabase データの保管庫 + 受付係。
データベース (回答や所属の保存場所) と、ログイン処理、 アクセス制御をまとめて提供するクラウドサービス。 		サーベイの回答・ユーザー・チーム・期間など すべての情報を保管していて、 「この人はリーダーだから自チームだけ見せる」といった ルールも Supabase の中で守られています。
Cloudflare
(Workers)		 アプリを世界中に届ける配達網。
Web サイトやアプリを実際にユーザーのブラウザに配信する グローバルなインフラ。 		Light Survey の URL を開いた時に、 画面を組み立ててブラウザに返してくれているのが Cloudflare Workers です。 サーバーを自前で用意せずに済むのが利点。
認証
(Google OAuth)		 ログインの仕組み。
「アクセスしてきた人が本当に Light の社員か」を Google アカウント経由で確かめる方式。 		Light の Google Workspace アカウントでログインし、 その人がメンバー / リーダー / 役員 のどれなのかを判定して、 見える画面・データを切り替える基盤。
RLS
(Row Level Security)		 データベースが自分で守る鍵。
直訳すると「行レベルのセキュリティ」。 データの 1 行 1 行に「誰が見ていいか」のルールを データベース自身が持っている仕組み。 		例えばメンバーが他人の回答を見ようとしても、 アプリのコードが間違っていたとしても、 データベース側で自動的に拒否される。 小さなチームで個人の回答が漏れないための 最後の砦になっています。
E2E テスト
(End-to-End)		 ロボットによる動作確認。
ブラウザを実際に自動で動かして、 「ログイン → 回答 → 送信 → レポート確認」を 通しでテストする仕組み。 		人間がいちいち全画面を触らなくても、 プログラムが勝手にメンバー / リーダー / 役員 の役で アプリを操作して「壊れていないか」を確認します。 機能追加のたびに自動で走る。
性能 (Performance) ページの軽さ・速さ。
表示までの待ち時間、サーバー負荷、データ取得の効率など、 「待たされない / 落ちない」をつくる作業。 		例えば「リーダーレポートを開く時に、 内部で 6 回データベースに問い合わせていたのを 1 回にまとめる」 など、ユーザーが体感する速さに直結する地味だが重要な改善。
CI / CD 自動チェック + 自動公開のベルトコンベア。
コードを GitHub にアップした瞬間に、 テスト → ビルド → 本番反映までを自動で流す仕組み。 		楢木さんがコードを書いて main ブランチにマージすると、 自動で Cloudflare に反映され、本番環境が更新される。 「リリース作業」を人手でやらなくて良くなる。
data-source 層
(モック / 本番の切替)		 データの取り出し口を 1 つに揃える設計。
画面側からは「データをくれ」と言うだけで、 裏が Supabase なのか架空データ (モック) なのかを 気にしなくて良くする層。 		Supabase を使わずローカルだけで全画面が触れる 「モックモード」を成り立たせているのがこの設計。 開発・デモ・テストが安全にできるようになっています。
リファクタ
(DDD 化)		 機能を変えずに中身を整理整頓。
外から見える動きはそのままで、 コードの構造を読みやすく・直しやすくする作業。 		コードが大きくなってきた時に、 「この大きなファイルを役割ごとに分ける」「同じことを 書いている部分を 1 箇所にまとめる」など、 将来の開発スピードを保つための投資。

💡 やってみて分かったこと

  • 「見映え」と「基盤」は別スキル。 画面のコピーや表示順を直すのと、DB のテーブル設計や RLS を書くのは 必要な脳の使い方が全然違うと体感した。
  • モックモードがあると開発が爆速になる。 Supabase に繋がなくても画面で確認できるので、思いついたアイデアを その日のうちに動かせる。これは楢木さんが Phase 1-4 で 整えてくれた基盤の恩恵。
  • Claude Code は「楢木さんの分まで書いてくれる相棒」になり得る。 これまで自分の手に余っていた DB スキーマ・認証・API・テストといった コード作業を、Claude に指示すれば書いてもらえる。 ただし「Resend のアカウント作成」「Cloudflare 管理画面の操作」のように 人間にしかできない作業は残る。そして何より、 「何を作りたいか」を具体的に言葉にできないと、Claude も 的外れなコードを出してくる —— コードが書けるかより、 何を作るべきか言える力が問われるようになった。
  • PR を小さく分けると後で読みやすい。最初は機能を 一気に詰め込んでいたが、楢木さんの PR を見ていると 1 PR = 1 目的で 分割されていて、後から振り返る時の負荷が全然違う。

🌐 「楢木さん的な作業」は本来どんな職種が担っていたか

ここで言う「楢木さん的な作業」を世の中の職種に当てはめると、 本来 専門のソフトウェアエンジニアを雇う必要があった領域 にあたります。

領域 これまでの担い手 (一般的な職種) 本来の必要リソース感
DB スキーマ + RLS バックエンドエンジニア / DB エンジニア 専任で実務 3-7 年クラスが必要
API + 認証 バックエンド / フルスタックエンジニア 同上
Cloudflare / Supabase 運用 インフラエンジニア / SRE / DevOps 専任 or 兼任の社内インフラ担当
E2E テスト整備 QA エンジニア / SDET 専任の品質保証担当
セキュリティハードニング セキュリティエンジニア 専任 or 外部監査
アーキテクチャ設計 / リファクタ テックリード / シニアエンジニア 実務 7 年以上の上級職

ざっくり言えば「Web アプリのバックエンド〜運用全般を見る人」 = バックエンド / フルスタックエンジニア。Light Survey 級の 社内アプリを 1 から立ち上げる場合、本来は 専任のエンジニアを 1 人 (採用までに半年〜) 確保するか、外注する必要があった領域です。

🚪 非エンジニアの萩原がこの領域に踏み込めるようになった意味

  • 専任エンジニアを雇わずに業務アプリを立ち上げられる —— これまで「事業会社が内製で何か作る」には、まず採用が壁だった。 Claude Code + 萩原のような業務理解者がいれば、最初の一歩を踏み出せる。
  • 仕様 → 実装の伝言ゲームがなくなる —— 「事業を理解している人」と「コードを書く人」が別人だと、 必ず認識のズレが起きる。同じ人が両方できると、 ピントの合った機能がすぐ出る。Light Survey のリーダー表示範囲のように、 業務側でないと気づけない仕様が即座にコードに反映される。
  • エンジニアの役割は「実装作業者」から「設計判断者・品質保証者」へ。 楢木さんが PR #181 で見せたような「仕様の抜けを実装で守る」役割は、 Claude では完全には代替できない。むしろエンジニアの価値が 「コードを打つ手」から「正しい設計判断ができる頭」に移っている。
  • 業務側人間が「両方できる」のは強力 —— ビジネス要件と技術判断を 1 人で握れる人材は、これまで CTO クラスの 一部しか存在しなかった。Claude Code でそれが事業会社の現場でも 成立しはじめている、というのが今回の数ヶ月の手応え。

コードと運用の分離 (#119) 招待メール Resend 連携を書く時に、「自分のスコープ (コード)」と 「楢木さん依頼 (API キー / ドメイン認証 / Secret 登録)」を PR の本文で最初から分けて明記。 キーが揃わない間は no-op フォールバックで壊れないよう実装した。 外部サービス連携は「コードが書けた = 動く」ではない ことを最初から認識し、ハンドオフを設計に組み込んだ。後追いではなく 先回りで段取りを書いた点が良かった。
ダッシュボード機能の PR 分割 (#100 / #101 / #102) 加重総合スコア + フィルタ / 期間切替 + チーム集計 + 月次マトリックス / メンバー個別詳細、と機能を 3 つの PR に分けて 2 日かけて投入。 1 PR にまとめず別々にレビューしやすくした。 後から見た時に「いつ何を入れたか」が辿りやすい。 バグが出た時の切り分けや revert も PR 単位でできる。
Claude Code との協業 #92 / #119 など複数 PR で Claude を co-author として明記し、 「何を作りたいか」を自分で言語化、コードは Claude に書かせる スタイルで実装スピードを出した。 非エンジニアでも「設計判断する人」として開発に参加できる ことを実証。書ける道具 (Claude Code) があれば、コードを書けるか否か ではなく 何を作るべきかを言える人 の価値が大きい。
もくもく会で仕様を言語化 (PR #181 #183 の発端) 本番環境を 3 人で触りながら、「リーダーには自己評価だけ見せる」 「役員には管掌範囲スコープと注力配分を出す」など、コードを見ない ユーザー目線の仕様を Notion にメモとして残した。 使ってみて初めて分かる違和感を、設計に戻すループ を作れた。結果として楢木さんが PR #181 / #183 にすぐ落とし込めた。

🙏 楢木さんに助けられたところ

  • Phase 0-4 のセットアップ — Next.js + Supabase + Cloudflare のテンプレを最初に組んでくれていたので、自分は最初から 「画面を作る」段階に入れた。
  • RLS とセキュリティの徹底 — メンバーが他人の回答を 見ようとしても DB レベルで止まるよう、すべてのテーブルに RLS を入れて くれていた。自分が画面側で漏らしても、最後の砦が効く。
  • 性能の自動最適化 — レポート / ダッシュボード周りの データ取得を、楢木さんが RPC 化 (#146) や React cache 化 (#152) などで自然に速くしてくれた。萩原が機能を足した部分も含めて、 気づいたら裏で軽くなっている状態。
  • 仕様の言語化への伴走 — もくもく会で議論した内容を すぐ PR #181 / #183 として実装に落としてくれて、設計から実装までの ループが短い。

🎯 これから自分が伸ばしたいこと

  • DB スキーマと RLS を読めるようになる — 楢木さんのレビューで何を指摘されているかを、自分の頭で 理解できる状態に。
  • 「リリースまでの段取り」を最初に書く — コードだけでなく、秘密情報・本番反映・運用切替まで含めて 完了の定義をする。
  • 影響範囲の見渡し — 「ここを直すと別の場所が壊れる」を 事前に Claude や grep で洗い出してから手を動かす。
  • 非エンジニアにも伝わる仕様書を残す — もくもく会で やったように、画面キャプチャ + 文章で「誰に何が見えるか」を 明示する習慣をつける。
