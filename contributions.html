用語解説 (非エンジニア向け)

以降の説明に出てくる技術用語を、家・お店に例えて先にまとめます。

用語 ひとことで言うと Light Survey での役割
Supabase データの保管庫 + 受付係。
データベース (回答や所属の保存場所) と、ログイン処理、 アクセス制御をまとめて提供するクラウドサービス。 		サーベイの回答・ユーザー・チーム・期間など すべての情報を保管していて、 「この人はリーダーだから自チームだけ見せる」といった ルールも Supabase の中で守られています。
Cloudflare
(Workers)		 アプリを世界中に届ける配達網。
Web サイトやアプリを実際にユーザーのブラウザに配信する グローバルなインフラ。 		Light Survey の URL を開いた時に、 画面を組み立ててブラウザに返してくれているのが Cloudflare Workers です。 サーバーを自前で用意せずに済むのが利点。
認証
(Google OAuth)		 ログインの仕組み。
「アクセスしてきた人が本当に Light の社員か」を Google アカウント経由で確かめる方式。 		Light の Google Workspace アカウントでログインし、 その人がメンバー / リーダー / 役員 のどれなのかを判定して、 見える画面・データを切り替える基盤。
RLS
(Row Level Security)		 データベースが自分で守る鍵。
直訳すると「行レベルのセキュリティ」。 データの 1 行 1 行に「誰が見ていいか」のルールを データベース自身が持っている仕組み。 		例えばメンバーが他人の回答を見ようとしても、 アプリのコードが間違っていたとしても、 データベース側で自動的に拒否される。 小さなチームで個人の回答が漏れないための 最後の砦になっています。
E2E テスト
(End-to-End)		 ロボットによる動作確認。
ブラウザを実際に自動で動かして、 「ログイン → 回答 → 送信 → レポート確認」を 通しでテストする仕組み。 		人間がいちいち全画面を触らなくても、 プログラムが勝手にメンバー / リーダー / 役員 の役で アプリを操作して「壊れていないか」を確認します。 機能追加のたびに自動で走る。
性能 (Performance) ページの軽さ・速さ。
表示までの待ち時間、サーバー負荷、データ取得の効率など、 「待たされない / 落ちない」をつくる作業。 		例えば「リーダーレポートを開く時に、 内部で 6 回データベースに問い合わせていたのを 1 回にまとめる」 など、ユーザーが体感する速さに直結する地味だが重要な改善。
CI / CD 自動チェック + 自動公開のベルトコンベア。
コードを GitHub にアップした瞬間に、 テスト → ビルド → 本番反映までを自動で流す仕組み。 		楢木さんがコードを書いて main ブランチにマージすると、 自動で Cloudflare に反映され、本番環境が更新される。 「リリース作業」を人手でやらなくて良くなる。
data-source 層
(モック / 本番の切替)		 データの取り出し口を 1 つに揃える設計。
画面側からは「データをくれ」と言うだけで、 裏が Supabase なのか架空データ (モック) なのかを 気にしなくて良くする層。 		Supabase を使わずローカルだけで全画面が触れる 「モックモード」を成り立たせているのがこの設計。 開発・デモ・テストが安全にできるようになっています。
リファクタ
(DDD 化)		 機能を変えずに中身を整理整頓。
外から見える動きはそのままで、 コードの構造を読みやすく・直しやすくする作業。 		コードが大きくなってきた時に、 「この大きなファイルを役割ごとに分ける」「同じことを 書いている部分を 1 箇所にまとめる」など、 将来の開発スピードを保つための投資。

💡 やってみて分かったこと

  • 「見映え」と「基盤」は別スキル。 画面のコピーや表示順を直すのと、DB のテーブル設計や RLS を書くのは 必要な脳の使い方が全然違うと体感した。
  • モックモードがあると開発が爆速になる。 Supabase に繋がなくても画面で確認できるので、思いついたアイデアを その日のうちに動かせる。これは楢木さんが Phase 1-4 で 整えてくれた基盤の恩恵。
  • Claude Code は「自分の代わりに楢木さんの分も書いてくれる相棒」 になり得る。ただし設計判断 (何をどう見せるか) は人間が言語化しないと 良いものが出てこない。
  • PR を小さく分けると後で読みやすい。最初は機能を 一気に詰め込んでいたが、楢木さんの PR を見ていると 1 PR = 1 目的で 分割されていて、後から振り返る時の負荷が全然違う。

🔧 つまずいた作業 (と、そこから学んだこと)

つまずき 何が起きたか 学び
リーダーレポートの表示範囲 「リーダーには自分のコンディション・自己評価・期待ギャップだけ」 という仕様を、最初の実装ではメンバー評価まで見える形にしてしまった。 小チームで個人特定リスクがあったため、もくもく会で発覚 → 楢木さんが PR #181 でデータ層に isSelfView マスキングを実装。 「誰に何を見せないか」は実装前に書き出す。 プライバシー要件は UI の後ろの DB アクセス層で守らないと、 画面を変えただけだと API レベルで漏れる。
デモデータ削除スクリプト PR #104 でデモデータ削除スクリプトを書いたが、外部キー (FK) の影響範囲を allowlist まで広げていなかったため、 楢木さんが PR #106 で修正してくれた。 データを消す系の操作は影響範囲のチェックが命。 テーブル単体ではなく、関連テーブルまで見渡す癖が必要。
招待メール (Resend) 連携 PR #119 で Resend 連携を書いたが、API キーの発行・本番反映 までの段取りが分かっておらず、楢木さん側の作業を 何度かお願いすることに。 機能を書く時は「リリースまでに誰が何をするか」も セットで考える。コードが書けても、秘密情報 / ドメイン認証 / 本番反映が揃わないと動かない。
エンゲージメント軸名のリネーム PR #103 で軸名を変えたが、影響範囲が画面・集計・DB ラベル・ ドキュメントに散らばっていて、抜け漏れが出ては修正を繰り返した。 ラベル変更は「文字列を grep して全部書き換える」だけでは不十分。 DB に保存されている過去データとの整合も考える必要がある。
ダークモードのコントラスト PR #97 でサーベイ画面を直したが、レポート画面でも同じ問題が 出ていることに気づかず、PR #99 で追っかけ修正。 UI の修正は「同じパターンが他にもないか」を最初に探す。 1 箇所直したら、横展開できる箇所を一気に潰す方が結局速い。
AI 統合 (Anthropic SDK) PR #92 で SDK 基盤を入れた直後、楢木さんが PR #96 で NODE_ENV ガードや Zod parse などのレビュー指摘を反映してくれた。 外部 API を叩くコードは「動く」と「本番で安全に動く」の間に 大きな差がある。環境変数の取り扱い、レスポンス検証、 エラーログの粒度を最初から意識する必要がある。
